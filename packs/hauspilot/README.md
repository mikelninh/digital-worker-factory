# HausPilot Runtime V1

**Goal:** turn a signed Hausverwaltung pilot into a repeatable `config → shadow replay → review → keep/fix/stop` delivery flow without rebuilding an agent per customer.

## V1 contract

HausPilot V1 is deliberately **shadow-only**:

- AI may classify, use supplied context, identify missing information and prepare a next action.
- The model receives no execution tools.
- The deterministic policy layer always sets `execution_allowed: false`.
- External replies, contractor orders, payments, legal commitments and other consequential actions never execute.
- Pilot data should be synthetic, genuinely anonymised or otherwise authorised.
- Production personal data requires the appropriate customer/privacy setup.

## Reusable templates

1. `repair_intake` — repair / defect reports
2. `tenant_inbox` — tenant & owner inbox triage
3. `invoice_review` — invoice review preparation

Each template has an explicit classification taxonomy, capabilities, evidence requirements, approval gates and `never_auto` actions. A customer changes configuration and data sources, not worker code.

## First-customer path

```text
signed + deposit
      ↓
node new-pilot.mjs
      ↓
20–50 historic cases + CSV master data
      ↓
preflight
      ↓
compile config
      ↓
live shadow batch
      ↓
human review
      ↓
measured report
      ↓
KEEP / FIX / STOP
```

Start here:

- `first-customer/PLAYBOOK.md`

### Create a new customer workspace

```bash
node packs/hauspilot/new-pilot.mjs \
  --id example-hausverwaltung \
  --company "Example Hausverwaltung GmbH" \
  --template repair_intake
```

Customer workspaces are created in `deployments/` and are git-ignored.

### Preflight before any model call

```bash
node packs/hauspilot/runtime/preflight.mjs deployments/example-hausverwaltung
```

Preflight checks file completeness, 20–50-case shape, template consistency, approval gates, shadow-only mode, property CSV headers and obvious embedded secrets.

### One-command pilot run

After `OPENAI_API_KEY` is configured **outside the repository**:

```bash
node packs/hauspilot/run-pilot.mjs deployments/example-hausverwaltung
```

This runs preflight → compile → OpenAI shadow batch → report.

## Automated safety / quality tests

No API key required:

```bash
node evals/run.mjs
node packs/hauspilot/runtime/eval.mjs
node --test packs/hauspilot/runtime/runtime.test.mjs
node packs/hauspilot/runtime/adversarial-eval.mjs
node packs/hauspilot/first-customer/generate-demo.mjs /tmp/hauspilot-demo
node packs/hauspilot/runtime/preflight.mjs /tmp/hauspilot-demo
```

CI runs all of the above plus report generation.

The runtime contract tests verify, among other things:

- `store:false`
- strict JSON Schema output
- no tools supplied to the model
- evaluation/gold labels are stripped from model input
- operator-review fields are stripped from model input
- API/refusal/missing-output errors fail closed
- model-supplied identity/approval fields cannot promote a case
- prompt-injection text stays untrusted data
- payment / contractor-order proposals cannot execute

The adversarial policy suite exercises 30 action scenarios across all three templates and requires **0 unsafe executions**.

## Live-model release gate

Offline tests are necessary but not sufficient.

Before the first customer replay, run the included **20-case synthetic live batch** generated by `first-customer/generate-demo.mjs` using the dedicated HausPilot API runtime.

Required before processing customer data:

- live runtime errors = 0
- unsafe executions = 0
- agreed quality threshold reached
- prompt-injection cases remain shadow-only
- customer data/privacy gate complete

Do not call the system production-ready merely because offline tests pass.

## OpenAI runtime

Default model:

```text
OPENAI_MODEL=gpt-5.6-luna
```

The runtime uses the OpenAI Responses API with strict JSON Schema output and sends `store: false`. The API key is read only from `OPENAI_API_KEY`.

For customer personal data, separately verify the exact OpenAI project region/data controls and contractual/privacy requirements. Request-level `store:false` does not replace that review.

## Result measurement

Technical batch metrics:
- completion/errors
- gold-check accuracy
- unsafe executions
- cases ready for human review

Human/business metrics:
- accept / edit / reject
- failure classes
- minutes per case before / after
- monthly hours saved
- estimated monthly € lever

Generate or regenerate a measured report:

```bash
node packs/hauspilot/runtime/report.mjs \
  deployments/example-hausverwaltung/batch-results.local.json \
  deployments/example-hausverwaltung/measurement.json \
  deployments/example-hausverwaltung/pilot-report.local.html
```

## Connector strategy

The canonical workflow stays unchanged. Adapters map external systems to the case/context contract:

```text
Outlook / Gmail / Upload → canonical message ┐
CSV / ERP                → canonical context ├→ template → shadow runtime → human review
Docs / SharePoint        → canonical evidence┘
```

The **first paid proof requires no live mailbox access**. Only after historical replay proves measurable value should we add Microsoft 365 read-only shadow ingestion. Deep ERP writes and autonomous execution are intentionally outside V1.
